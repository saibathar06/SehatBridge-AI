# Architecture

The Expo Router application has five persistent tabs: Home, Treatments, AI Assistant, Appointments and Profile. Upload, Documents, Review, Treatment Details, Medicine Tracker, Settings and Pharmacy are stack routes. All screens use the authenticated API; synthetic provider data exists only in the labelled demonstration endpoints.

FastAPI owns authentication, patient isolation, encrypted records, private documents, confirmed plans, dose history and reminder intent. PostgreSQL is the production system of record. Redis performs atomic distributed rate limiting. A separately supervised worker claims document jobs using row locks, a bounded lease and limited attempts. Queued jobs survive API restarts; interrupted processing can be reclaimed after its lease expires. API processes do not launch ephemeral background jobs.

Documents have an explicit ordered page table. Images are signature-validated, decoded, stripped of EXIF metadata and saved as encrypted JPEGs. PDFs are parsed, split into one-page PDFs in their original sequence, and privately encrypted. The official Google GenAI SDK sends bounded batches of ordered pages with absolute page labels. Strict Pydantic output validation checks source ranges, uncertainty and critical missing fields. Cross-batch repeated medicine names are flagged for professional review. No semantic deduplication silently combines potentially conflicting instructions.

`gemini_service.py` is the replaceable provider adapter. `worker.py` orchestrates extraction and validation. `patient_context_service.py` retrieves authenticated confirmed records; `question_router_service.py` answers routine questions deterministically and uses Gemini for grounded explanations. `medicine_information_service.py` is a fail-closed verified-reference boundary. Native STT and TTS are isolated in the mobile assistant. Raw audio is not sent to or stored by SehatBridge. The Android speech engine may use its own network service.

Unreviewed `document_analyses` never become `treatments` without an explicit, revision-checked confirmation. Medicines, schedules, dose instances and append-only dose events are separate. Schedule edits deactivate old schedules and cancel upcoming doses while retaining history. Medicine index is persisted explicitly. Dose materialization serializes per user and has a unique schedule/timestamp constraint.

Only simple daily schedules are supported initially. The backend checks a recognized daily frequency and matching number of distinct times; weekly, tapering, interval and as-needed instructions remain unscheduled. Schedules require explicit start/end dates, timezone and timing confirmation; dates are limited to a year per schedule. DST nonexistent wall times are skipped and repeated wall times use their first occurrence. Calendar-based interval regimens need an additional model before activation.

Local notifications are a delivery queue, never the source of truth. Reconciliation reads server intent, deduplicates and cancels old alerts, and schedules up to 48 future alerts within seven days. App startup, foreground, periodic foreground activity and treatment/preference edits trigger reconciliation. Opening a notification never marks a dose taken. Remote FCM is an alternative selection, with generic text and per-device delivery records. It is not layered blindly on local alerts.

The UI follows the supplied cream/light-pink surfaces, rounded cards, compact medication rows, source review sections and chat layout. The written brief's pink primary / teal secondary palette takes precedence over the screenshots' mostly green primary buttons. No real patient names or treatment examples from the screenshots are seeded into patient screens. The application shell is English; Hindi/English preference currently applies to the voice/text assistant.

Dependency choices were checked against the current npm registry and Expo's bundled compatibility table. See [Expo notifications](https://docs.expo.dev/versions/latest/sdk/notifications/), [native speech-recognition installation](https://github.com/jamsch/expo-speech-recognition), [Gemini document inputs](https://ai.google.dev/gemini-api/docs/document-processing), [structured output](https://ai.google.dev/gemini-api/docs/structured-output), and [Gemini 3.5 Flash capabilities](https://ai.google.dev/gemini-api/docs/models/gemini-3.5-flash).
